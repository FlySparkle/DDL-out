## 当前项目快照

- 项目是使用 Flutter、Riverpod、Drift 和 Material 3 构建的本地优先截止事项
  看板，应用 ID 为 `com.flysparkle.ddlout`。
- 本文建立时的已提交基线为 `v0.4.2+1`，当前功能分支为 `远程同步更新`，提交
  `124ac5e` 是同步实现开始前的基线。
- Windows 和 Android 是主要开发、验证与发布目标；仓库同时保留其他 Flutter
  平台宿主。
- 数据默认存储在本机 SQLite 中，时间戳使用 UTC，显示时转换为设备本地时区。
- 核心行为包括分类和事项 CRUD、完成状态、截止时间排序、分类折叠、跨分类拖放、
  分类排序、清除已完成事项以及相对/绝对截止时间输入。
- JSON 全量备份仍是跨平台离线迁移方式。局域网同步是在此基础上新增的可选能力，
  不能让应用依赖网络才能使用。

## 历史演进与仍然有效的决定

### 早期 Python 版本与 Flutter 重写

项目最初是 Flask、SQLite 和 WebView 组合的桌面应用。早期工作保存了可运行基线，
清理了未完成的移动端/PWA 痕迹，并完善了相对时间自动进位和滚轮加直接输入的截止
时间控件。这一套 Python/WebView 实现已经被 Flutter 重写取代，旧代码和旧窗口
强制固定方案不再是实现依据；其中的产品行为只能作为体验参考。

Flutter 重写确立了以下长期方向：

- 本地优先，无账号也能完整使用。
- Riverpod 管理状态，Drift 管理 SQLite，Material 3 作为组件与主题基础。
- 领域、状态和数据层尽量跨平台复用，平台差异放在宿主和适配层。
- 小组件保持展示职责，截止时间计算、排序、合并和持久化放在组件之外。
- 中文、英文、日文文案通过 Flutter 本地化资源维护，文本文件统一使用 UTF-8。

首个 Flutter 版本从空数据开始，没有自动导入早期 Python 数据库。除非另有明确的
迁移需求，不应重新引入旧数据库自动迁移逻辑。

### UI 与交互演进

已经落地并应保留的体验包括：

- 设置入口并入 Material 3 导航体系，主页和设置共享响应式应用级导航。
- 字体和字号可配置；Windows 默认使用适合系统显示的字体回退方案。
- 分类使用原生彩色 `Card`，而不是旧版自绘边框。
- 分类支持拖拽排序并持久化；每个分类可以经确认后单独清空事项。
- 输入框的静止、悬停、聚焦和错误状态具有足够的背景对比度。
- 边栏行为以 [ADR 004](adr/004-responsive-navigation-modes.md) 为准：浮动与固定
  两种模式共享导航语义，并根据窗口宽度降级、收起或展开。

旧任务中“自适应桌面侧栏仅在 PC 显示、移动端完全保持原样”的中间方案已被后续
ADR 004 取代，不能据此回退现有导航实现。

### 本地构建环境经验

- 当前仓库迁移到纯英文路径，是因为旧路径中的中文和全角感叹号曾导致 Flutter、
  Dart AOT、Kotlin 增量缓存和 MSBuild 出现路径编码或跨盘问题。
- 在包含非 ASCII 字符的路径执行 Drift 代码生成时曾需要
  `dart run build_runner build --force-jit`；在当前英文路径仍可保留该选项以提高
  稳定性。
- Flutter Windows 插件通常需要符号链接权限。开启 Windows 开发人员模式是长期
  方案；无法开启时，曾用 `windows/flutter/ephemeral/.plugin_symlinks/` 下的
  Junction 临时完成构建。该目录会被 `flutter clean` 删除，因此 Junction 只是
  故障处理手段，不是仓库组成部分。
- Android 工具链需要 JDK 21、Android SDK、已接受的许可证及兼容的插件版本。
  历史上曾因 AGP/Kotlin 兼容性固定 `file_picker` 版本；当前依赖以
  `pubspec.lock` 和 [ADR 001](adr/001-android-kotlin-compatibility.md) 为准。
- 不要提交 `.dart_tool/`、`build/`、`windows/flutter/ephemeral/` 或旧的嵌套
  `ddl_out_flutter/` 构建残留。

### GitHub 与发版规则

- 普通功能开发在分支提交并推送，经 PR 和 CI 合入 `main`；单纯 `git push` 不会
  创建 Release。
- Flutter 版本采用 `主版本.次版本.修订版本+构建号`。用户版本标签不包含构建号，
  例如 `pubspec.yaml` 中 `0.4.2+1` 对应 Git 标签 `v0.4.2`。
- 正式发布前必须确认版本提交已经进入 `main`，再把准确的合并提交标记为 `v*` 并
  推送标签。标签触发 GitHub Actions 构建与创建 Release。
- 应用内更新以 [ADR 005](adr/005-in-app-updates.md) 为准。Windows 使用自包含便携 ZIP，
  Android 使用相同应用 ID 和签名密钥的 APK，发布资产必须包含并通过 SHA-256
  校验。
- 不把本地调试 APK、签名材料、用户数据库、代理设置或临时构建目录提交到仓库。

## 当前局域网同步工作

### 产品与安全边界

当前方向是不建设账号或付费云服务，而是在同一局域网内由电脑显示二维码、手机
扫码后点对点同步。该功能必须保持可选，并维持应用离线可用。已采纳的具体决策见
[ADR 002](decisions/002-lan-peer-sync-and-conflicts.md)：

- 电脑生成两分钟有效的一次性二维码，手机通过 WebSocket 直连。
- 二维码携带随机 256 位会话密钥，同步消息使用 AES-GCM 加密，不经过云端。
- 实体使用跨设备 UUID；修改记录为不可变操作，并用版本向量判断因果关系。
- 两端只交换对方缺少的操作；不同字段的并发修改自动合并。
- 同一字段出现并发不同值时保留候选值并建立显式冲突，不使用最后写入覆盖。
- 删除通过墓碑传播，并发删除暂时优先，避免事项意外复活。
- 生成二维码的电脑默认审批冲突，用户可以主动把审批权切换到手机；审批决定本身
  也作为同步操作传播。

### 实现状态

同步功能已经在旧目录中实现后迁移到当前英文目录，但在本文建立时仍是未暂存、
未提交的工作区改动，用户要求先查看效果。当前改动涉及数据库同步元数据、操作日志、
字段头和冲突表，局域网会话与加密传输，设置入口、设备管理和冲突审批界面，以及
合并测试。开始后续工作前必须先运行 `git status`，不得把这些改动误认为已进入
`v0.4.2` 或远程仓库。

数据库继续保留现有本地整数主键供 UI 使用，同时增加同步 UUID。恢复 JSON 全量
备份前需要先解除配对设备，避免恢复后的实体身份与其他设备保存的同步历史不一致。
